## Engineering constraints

- Booking Authority remains the only authority for appointment placement, capacity validation, capacity locks, and customer-facing appointment identity.
- Communication Authority / transactional WhatsApp services remain the outbound communication authority.
- Canonical workforce records remain the source for van crew identity: `staffProfiles`, dated `dailyVanAssignments`, plus canonical Van fallbacks.
- No browser-only or WhatsApp-only scheduling authority may be introduced.
- Existing business rules remain unchanged unless explicitly listed under Approved changes below.
- Preserve transaction-time revalidation, idempotency, conflict prevention, support/primary linkage, audit history, and single customer communication ownership.
- No patch-on-patch implementations or duplicate duration/capacity formulas.
- Self-review is required. There is no independent third-party reviewer gate for this repository/workstream.

## Protected existing rules

1. Flexible lunch overlap: lunch is not a hard booking blocker. A continuous job may span the lunch window. Lunch is not independently sellable as a normal customer slot.
2. Same-property Standard Service: primary Van capacity is 7 units under the existing canonical rule; overflow uses linked support assignment(s).
3. Support assignments never send duplicate customer confirmation/reminder messages. The primary appointment owns customer communication.
4. Support Van selection must honor real capacity and operational/routing policy, not merely any nominally free Van.
5. Half-day, company closure, Van unavailable, staff availability and commit-time capacity checks remain authoritative.
6. After-hours work is an explicit operational exception and must not become ordinary customer-bookable capacity.
7. No production merge/deploy, destructive migration, or production messaging is authorized by this branch.

## Architecture findings

### Canonical scheduling and time

- `functions/bookingCapacityAvailability.js` derives canonical occupied capacity and returns assignment `endTime` from occupied slots.
- `functions/bookingAuthorityWorkOrders.js` persists `scheduledSlots`, `appointmentEndTime`, `appointmentDurationMinutes`, and PRIMARY/SUPPORT role on each Work Order.
- `apps/erp-next/lib/live-scheduling.ts` projects schedule end using canonical reserved slots first, then explicit appointment end, then duration as a historical fallback.
- `functions/technicianDailyScheduleService.js` currently uses a different precedence for technician WhatsApp: duration is projected before most canonical schedule/end data. This is the identified root cause class for Scheduling UI vs technician WhatsApp end-time drift.
- Fix direction: one canonical schedule-span resolver/precedence for technician communication that agrees with Booking Authority/Scheduling projection. Work duration may still be used for lunch planning where required; it must not independently redefine the promised/reserved schedule span shown to technicians.

### Customer communication

- Customer confirmation/reminder rendering is already centralized through appointment/work-order communication services.
- Support Work Orders are initialized without customer notification ownership.
- The current evidence points specifically to technician daily-schedule time reconstruction, but all confirmation/reminder/reschedule paths require regression verification before completion.

### New Appointment validation

- `LiveAppointmentCreateDrawer` already calls canonical `checkOfficeCreateAvailability` via a manual `Validate target` action.
- The same endpoint can be invoked reactively/debounced as the operator changes a complete-enough booking target. Do not implement a second browser validation engine.
- Final create/confirm must retain server transaction-time revalidation.

### Crew identity

- `live-operational-capacity.ts` already exposes `liveVanCrew(state, vanId, dateKey)`, resolving dated `dailyVanAssignments` first and Van defaults second, with names from `staffProfiles`.
- Scheduling lanes already use this resolver. New Appointment should reuse it rather than invent another workforce lookup.

### Support Van

- Planned support is substantially implemented in the canonical scheduling engine.
- Standard Service policy already models 7 + remainder and exact support start candidates, with `candidateAvailability` as capacity authority.
- Work Orders already model `appointmentAssignmentRole: primary|support` and parent linkage.
- Required work is therefore primarily UX/lifecycle integration and ad-hoc support mutation, not a second support engine.

### Temporary Hold

- Legacy/compatibility status `Reserva temporal` is recognized by some communication/schedule code, but the active Booking Authority office action/lifecycle API currently has no first-class create-hold/confirm-hold transition.
- Temporary Hold must be implemented in Booking Authority as a real capacity-owning lifecycle state, not a browser-only flag. It must suppress customer confirmation/reminder until confirmed.
- Expiry policy is intentionally not invented in this workstream until an existing canonical policy is found or product owner explicitly chooses one.

### Ad-hoc rescue support

- Existing PRIMARY/SUPPORT Work Order model should be reused.
- A rescue support action should link a new SUPPORT resource assignment/Work Order to an existing appointment and reserve the selected supporting Van/time atomically.
- Both the support Van and primary Van require internal same-day schedule-change notices; no duplicate customer communication.

### After-hours

- Current regular schedule lanes expose only canonical operating slots.
- After-hours must be a separate explicit action, starting at/after the normal 17:00 boundary, with no required scheduled end for emergency work.
- Actual completion time must come from field/work-order execution and feed existing employee timesheet/overtime fields rather than from a fabricated planned duration.
- Existing attendance/payroll already stores `overtimeMinutes`/`overtimeHours` and calculates time after 17:00; integration should reuse this authority.
