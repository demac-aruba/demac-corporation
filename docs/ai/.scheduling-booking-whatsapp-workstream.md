2. Standard Service same-property primary capacity remains governed by the existing 7-unit rule; overflow remains linked PRIMARY/SUPPORT.
3. Support Work Orders never become a second customer appointment or customer communication owner.
4. Half-day, company closure, Van availability, dated crew/absence and transaction-time capacity validation remain authoritative.

7. Payroll overtime remains owned by the canonical Attendance calculation; Work Order completion contributes real work evidence rather than another overtime formula.

## Final architecture

### Continuous schedule-time authority / flexible lunch

`OPS-SCHED-LUNCH-001` is documented in `docs/ai/OPS_SCHED_LUNCH_001.md`.

- Normal customer starts remain `08:30`, `09:30`, `10:30`, `13:30`, `14:30`, `15:30`.
- Modern Work Order wall-clock time is `time + appointmentDurationMinutes`, with `appointmentEndTime` as its stored projection.
- `scheduledSlots` remains capacity/history metadata and a compatibility fallback; it is not a second modern timing authority.
- Booking Authority capacity uses continuous start/end intervals. Capacity locks use only sellable start anchors actually overlapped by that interval.
- `10:30 + 180 min = 13:30`; the `13:30` start remains available.
- `10:30 + 240 min = 14:30`; the `13:30` start is blocked.
- Lunch itself never becomes a customer-bookable `12:00`, `12:30`, or `13:00` slot.
- Full-day policy can reserve all sellable anchors without falsifying technician-visible wall-clock time.
- Live Scheduling, PENDIENTE and technician WhatsApp use the same continuous duration semantics.

### Technician daily schedule / PENDIENTE

- Technician messages no longer independently stretch scheduled time through lunch gaps.
- Sellable unused operational starts appear as `PENDIENTE`.
- Temporary Hold, real booked work, unavailable Van/crew, closure and half-day capacity remove the corresponding PENDIENTE capacity.
- Lunch is never emitted as an independently sellable PENDIENTE period.

### Same-day schedule changes

- The existing Work Order write boundary drives deterministic same-day Van-group alerts after the 08:00 schedule delivery.
- Work creation/material placement changes notify the correct Van without creating another customer communication path.
- Field execution status-only changes do not masquerade as schedule changes.

### New Appointment / live validation / crew

- New Appointment reuses Booking Authority `checkAvailability` reactively/debounced.
- Commit-time transaction validation remains mandatory and authoritative.
- Stale asynchronous browser validations cannot become confirmable.
- The drawer shows actual dated crew, including optional third helper where configured.
- Dynamic Van resolution supports future `VAN-n` lanes while resolving legacy Firestore document IDs through their real canonical Van record first.

### Temporary Hold

- `temporary_hold` is a first-class Booking Authority state using the same Appointment, Work Orders and capacity locks as confirmation.
- Holds reserve real capacity and display distinctly in Scheduling.
- No customer confirmation/reminder is eligible while held.
- Confirm preserves identity and verifies lock ownership before transition.
- Reschedule moves held capacity atomically while preserving hold state; cancellation releases it.
- Automatic expiry remains intentionally undefined (`NEEDS_HUMAN`). Current approved behavior is manual confirm/reschedule/cancel, so no timeout was invented.

### Planned Support Van

- Existing 7 + remainder PRIMARY/SUPPORT architecture was reused rather than replaced.
- Exact support alternatives come from real Booking Authority capacity/route validation.
- Primary remains responsible; support does not duplicate customer messaging.

### Ad-hoc same-day support

- An operator can choose a genuinely open same-day Van slot and `Send support to a coworker`.
- Booking Authority creates one linked `adhoc_rescue` SUPPORT Work Order and canonical lock under the existing appointment.
- Primary appointment, primary Van and customer-facing schedule remain unchanged.
- Support inherits customer/property/job context and is non-billable/no customer communication owner.
- Capacity, calendar, Van, dated crew, route, Work Order conflicts and concurrent locks are revalidated server-side.
- The support Van and primary Van both receive deterministic same-day internal alerts with actual dated crew/context.
- Future planned multi-Van jobs continue using the planned support engine rather than this same-day rescue action.

### After-Hours / Emergency

- Scheduling has a separate explicit After-Hours / Emergency action beginning at/after 17:00.
- It does not create ordinary customer-bookable post-17:00 slots.
- Emergency work is created without a fabricated scheduled end.
- One unresolved/open-ended emergency prevents overlapping unknown-duration emergency capacity on the same Van.
- Actual completion is recorded through the Work Order Application boundary and releases the open emergency capacity.

### Attendance / overtime

- Work Order completion contributes actual work segments/evidence to `employeeTimesheets`.
- The shared canonical Attendance runtime is the only overtime calculation authority.
- Existing Clock In/Clock Out/Break/schedule rules, partial missing-time Paid/NWNP classification and schedule snapshots remain intact.
- Work Order evidence is unioned with existing actual-time facts to avoid double-counting overlap.
