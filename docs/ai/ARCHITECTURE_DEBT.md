# Architecture Debt Register

| ID | Debt | Risk | Exit condition |
| --- | --- | --- | --- |
| AD-001 | Root package depends on sequential source-patching scripts before start/typecheck/build | Non-reproducible changes and fragile builds | Replace generated patch chain with reviewed source and clean deterministic build |
| AD-002 | Root/Legacy documentation contains stale descriptions, including old MVP/local-persistence assumptions, while production-capable Firebase functions coexist | Stale documentation can be mistaken for current architecture and create boundary/data-flow errors | Reconcile root/Legacy documentation against approved current authorities, mark superseded material, and publish an environment-specific runtime/data ownership map |
| AD-003 | Legacy and ERP Next duplicate product concepts | Rule drift and inconsistent identity | Canonical contracts and parity ledger cover every migrated module |
| AD-004 | Quality gates are fragmented across package scripts and path-filtered workflows | Changes can miss relevant validation | One documented, dependency-aware required check set |
| AD-005 | Multiple external communication and deployment paths exist | Duplicate messages or partial rollout | Single communication authority and deployment inventory with owners |
| AD-006 | ERP Next acceptance scripts generate temporary compiled directories | Cleanup and CI consistency risk | Adopt a standard test runner with isolated managed artifacts |
| AD-007 | Repository documentation is extensive but lacks uniform status/ownership metadata | Stale guidance may appear authoritative | Add owner, status, reviewed date, and supersession links to governing docs |
| AD-008 | ERP Next still contains fixed four-Van assumptions, including `VAN-1` through `VAN-4` patterns, fixed arrays, and `/4` metrics | Fleet growth or configuration changes can produce incorrect allocation, reporting, and UI behavior | Fleet behavior is data-driven end to end with no fixed fleet-size assumptions |
| AD-009 | Dispatch Control and Dispatch Readiness remain browser/local or hybrid rather than fully canonical live operational views | Operators can see stale or non-authoritative state and make inconsistent dispatch decisions | Both views read governed live operational models from canonical authorities, with reconciliation and failure behavior proven |
| AD-010 | Work Orders and Field/Technician execution retain browser, preview, or hybrid paths and have not achieved full Legacy parity | Field execution can lose state or diverge between preview and canonical workflows | Canonical persisted end-to-end Work Order and field execution flows pass approved Legacy parity scenarios |
| AD-011 | Technician Portal/mobile field workflow parity is incomplete, including technician agenda, evidence, measurements, reports, and Office Review | Technicians and office reviewers lack a proven complete operational path | Approved end-to-end parity evidence covers agenda, evidence, measurements, reports, and Office Review on the intended field surfaces |
| AD-012 | Older code, PR assumptions, and root/Legacy documentation can remain after architecture decisions change | Superseded architecture can be mistaken for current authority and reintroduced | Governing ADRs and authority documents have explicit supersession links, and stale code/document assumptions are classified and reconciled |
| AD-013 | The repository is currently public, while its licensing and intellectual-property posture has not been reviewed for proprietary engineering knowledge or a future commercial platform | Public exposure and unclear licensing may undermine confidentiality, ownership expectations, or commercialization options | An authorized human governance/legal review records the intended visibility, licensing, contribution, and IP posture; no automatic visibility or license change is implied |
| AD-014 | Privileged backend authorities do not yet share one canonical user-authorization contract; at minimum, Office Booking can fall back to token role claims when the canonical `users/{uid}` profile has no role and treats a missing `active` flag as allowed, while the hardened Communication Authority now requires an existing profile with `active === true` and an allowed canonical role | Authorization behavior can drift between authorities, allowing stale/custom token claims or incompletely provisioned user profiles to retain privileges on one backend surface after another surface would deny them | Adopt one reviewed backend authorization helper/contract for privileged ERP authorities that requires canonical profile existence, explicit active state, and allowed canonical role; migrate consumers with compatibility evidence and negative authorization tests rather than changing unrelated authorities opportunistically |
| AD-015 | Wacli outbound polling currently queries every `whatsappOutboundQueue` record for one communication account and filters provider/status/expired lease in memory before selecting a candidate | Firestore read cost and poll latency grow with historical queue size; sufficiently large retained history can make a 2-second poll cadence expensive or approach the 30-second poll timeout | Replace the account-wide scan with a bounded indexed active-queue query that preserves account/provider/outbound-class isolation and deterministic ordering; deliberately deploy any required Firestore index and define retention/archive behavior instead of weakening account filtering |

## Evidence / partial mitigations

### 2026-08-25 — Maya Communication V1.1 P0 architecture pass

- **AD-005 remains open.** The reviewed Wacli connector has one canonical account-bound Firebase boundary and the current DigitalOcean source is `ops/digitalocean/deploy/server-v2.mjs`. `.github/workflows/digitalocean-remote-ops.yml` stages that source on the guarded `main` path and `ops/digitalocean/run/task.sh` validates/deploys it through the restricted host command; `.github/workflows/wacli-webhook-deploy.yml` separately validates/deploys the Firebase connector boundary. `functions/wacliBridgeAccountBinding.test.js` verifies the account-bound bridge contract. Canonical communication-account configuration remains `businessSettings/whatsapp`; downstream Booking, Technician, and Maya consumers must not own duplicate account IDs.
- The older `services/whatsapp-bridge/server.mjs`, environment example, and systemd files remain in the repository because repository evidence proves the intended deployment path but does not by itself prove the exact files/environment currently installed on the live host. `services/whatsapp-bridge/README.md` classifies them as superseded and points to the current account-bound pull topology. **Residual risk:** an operator could still manually deploy the old artifacts. Exit still requires an authorized host/deployment inventory and safe removal or archival after live-host verification.
- **AD-012 remains open.** The stale bridge instructions were reconciled, but the superseded executable artifacts have not been deleted. The Wacli workflow also rejects resurrection of the retired Firebase-to-Droplet `sendQueuedWacliMessage` path, rejects a Wacli boundary dependency back into `demacCustomerTurn`, and rejects Communication Identity depending on Booking scheduling primitives.
- Communication concurrency epochs were moved from the Maya-specific `demacCustomerTurn` layer into neutral `demacCommunicationEpoch.js`; Wacli transport and Booking dispatch safety consume the neutral primitive. `demacCustomerTurn` reexports it only for compatibility, so there is one implementation rather than duplicated epoch logic.
- Generic `cleanText`/SHA-256 `hashId` primitives were moved out of `bookingSchedulingPrimitives.js` into neutral `demacCorePrimitives.js`. Booking reexports the same functions for compatibility. The neutral communication boundaries that have no Booking-domain responsibility — `demacCommunicationIdentity.js`, `wacliCommunicationBoundary.js`, and `communicationConversationAuthority.js` — consume the core primitive directly. The hashing/text-normalization algorithms are unchanged, so canonical communication IDs do not gain a migration merely because dependency direction was corrected. Some Maya orchestration modules still obtain these helpers through the Booking compatibility export; because those modules already integrate with Booking-domain workflows and there is still only one implementation, that is classified as non-blocking cleanup rather than a second source of truth or a P0 authority violation.
- Ingress verification now recomputes the deterministic canonical conversation document ID from account/channel/provider/remote identity before marking a message/conversation verified. This is a partial mitigation for cross-path identity drift, not a replacement for end-to-end ingress/replay acceptance evidence.
- Legacy global appointment-reminder endpoints remain as compatibility paths behind the Office Booking facade while ERP Next uses the per-recipient `appointmentCommunicationAuthority`. They are intentionally not duplicated/refactored further in this Maya P0 change. Removal requires separate parity evidence proving no remaining consumer depends on the legacy contract.
- **AD-004 remains open, but this pass closes concrete FP-009 gaps for the touched communication slice.** Customer Agent architecture tracks the neutral core plus Communication/Customer surfaces; Customer Agent Production tracks the exact neutral core/identity/epoch dependencies used by its existing deployed runtime; Wacli tracks core/identity/epoch and its deploy-change detection; Transactional WhatsApp and Office Booking track the neutral core plus canonical Communication identity; Van Schedule Architecture tracks the neutral core because Booking scheduling primitives consume it. This does not claim the repository-wide path-filter debt is solved.
- **Deployment ownership is intentionally incomplete for new P0 runtime triggers.** `functions/bootstrap.js` exports the new ingress/Observer/customer-voice surfaces, while the reviewed Customer Agent Production workflow still deploys and verifies only `processCustomerAgentInbound` and `processCustomerAgentReactivation`. No production workflow scope was widened in this architecture pass. Before any new P0 trigger is activated, an authorized human must approve the deployment inventory/cutover, confirm the production `communicationAccountId`, and set the deliberate customer-voice activation cutoff where applicable. Until then this remains a `NEEDS_HUMAN` rollout boundary, not an invitation to add an automatic deploy path.

### 2026-08-25 — Verify integration corrections

- **AD-014 opened; no scope expansion performed.** Pass 3 hardened `communicationConversationAuthority` so authenticated communication commands require an existing canonical `users/{uid}` profile, `active === true`, and an allowed canonical profile role; assignment targets must meet the same active/canonical-role contract. Focused negative authorization tests verify 401/403 behavior. During verification, `officeBookingAuthority` was confirmed to still use `requireOfficeRole(profile.role || decoded.role)` and only denies when `profile.active === false`. That inconsistency is real but belongs to a broader backend authorization convergence effort, not Maya Communication P0. The Office Booking implementation was therefore left unchanged in this phase and the residual risk is tracked here instead of applying an unrelated patch.
- Focused reruns after the Pass 3 corrections repeated `validate-customer-agent` and `validate-wacli-connector` only. Both passed; the Wacli deploy job remained skipped. This verifies the corrected code and idempotency/regression suites without invoking a production deployment path.
- Duplicate automation review found intentional parallel stages but no second customer-facing sender authority: `bootstrap.js` exports the read-only Observer separately from the single Customer Runtime wrapper; the shared voice transcription path converges completed transcripts back into the same runtime. Existing replay/lease/fingerprint/receipt protections remain the authority for suppressing duplicate command sends, duplicate observation work, and repeated same-version transcription. Trigger-level infrastructure E2E remains a separate P0 evidence gap and is not reclassified as complete by this verification.

### 2026-08-25 — Maya P0 production-readiness pass

- **AD-005 remains open and is a production activation blocker.** A push to `main` that contains this PR's Wacli changes can independently start `.github/workflows/digitalocean-remote-ops.yml` for the host bridge and `.github/workflows/wacli-webhook-deploy.yml` for Firebase connector Functions. Those workflows have no cross-workflow ordering guarantee. The account-bound bridge is backward-compatible with the prior Firebase endpoint because it only adds Bearer/account headers, while the new Firebase gateway intentionally rejects a bridge that omits the account header. Therefore a direct merge is not a safe cutover mechanism: an authorized rollout must stage/verify the bridge account binding before activating the account-bound Firebase gateway and canonical identity writes, with outbound drained/controlled and migration evidence as required by the Maya implementation record. No workflow was modified or triggered to perform that rollout in this pass.
- **AD-005 also remains open because `communicationConversationAuthority` has no reviewed production deployment owner.** Customer Agent Architecture validates the `demacCommunication*.js` surface, but Customer Agent Production deploys only `processCustomerAgentInbound` and `processCustomerAgentReactivation`; the reviewed Wacli, Transactional WhatsApp, and Office Booking workflows deploy their own explicitly named functions and do not deploy `communicationConversationAuthority`. ERP Next already targets `https://us-central1-demac-corporation.cloudfunctions.net/communicationConversationAuthority` for claim/assign/return/close/status/read/send commands. Before the frontend/backend cutover is activated, an authorized human must assign this Function to an explicit deployment owner/order and verify the endpoint is ACTIVE/auth-protected; adding it opportunistically to an existing production workflow is not authorized by this branch.
- **Communication Authority is not yet an unbypassable production write boundary.** Current `firestore.rules` still allows operations roles to update the permitted ownership/status fields of `communicationConversations` and to create `whatsappOutboundQueue` documents directly. The same generic `businessSettings/{settingId}` write rule lets operations roles change Maya pilot/voice/autonomy settings. The branch intentionally does not change production access/security rules without human approval. Before production activation, an authorized security-rule cutover must remove/limit those direct critical writes after proving all intended clients use the backend authorities; otherwise FP-002 remains possible despite the hardened server path.
- **AD-015 opened as scalability debt, not a reason to widen this P0.** `claimOutboundCommandWithDb()` currently queries all queue records for `communicationAccountId` and then filters provider/status/lease/order in memory. This is correct and fail-closed for a controlled low-volume pilot, but it is not the long-term scalable polling shape. A bounded indexed query may require a production Firestore index, which belongs to an explicit human-approved infrastructure change rather than an opportunistic performance patch.
- Existing observability is adequate for a controlled pilot but not a substitute for rollout ownership. The DigitalOcean `/health` response exposes account binding, pending webhook/dead-letter/ACK counts and last forward/send/media/poll errors; Firebase records webhook processing outcomes, queue authorization failures, ownership command receipts/history, Observer status, transcription status, Case state and dispatch-hold provenance. No parallel audit store or dashboard was created. A production runbook should alert/escalate on nonzero dead letters/pending ACKs, repeated transcription/Observer failures, outbound authorization failures, stale dispatch holds and bridge account/connector errors.
- Existing rollback remains intentionally asymmetric. Before identity activation, normal code rollback is possible. After canonical account-scoped IDs are activated, rollback must disable Maya/voice/reply capabilities or pause the affected bridge rather than reverting ingress to legacy raw-chat IDs and creating split-brain writes. The repository does not contain evidence of an automatic host rollback command for `server-v2.mjs`; live-host rollback/recovery ownership must therefore be confirmed by the authorized deployment operator before cutover.
- **P0 is not production-ready yet.** The non-blocking persistent debounce is now implemented: `eligibleAt` is derived from the canonical inbound time, the approved 10–15 second window defaults to 12 seconds, Cloud Tasks is wake-up transport rather than business truth, and current-turn/ownership checks suppress stale wake-ups without sleeping. Required automated acceptance coverage is wired into the mandatory Customer Agent gate, including the named race scenarios. Production activation is still blocked by trigger-level rollout/inventory approval, production `communicationAccountId` and bridge binding verification, deliberate voice activation cutoff, Communication Authority/security-rule cutover, staged deployment ordering, and independent Reviewer evidence. Customer voice activation also currently has a 25 MB media limit and bounded retry count but no approved duration-based cost limit; if DEMAC requires a duration ceiling for pilot cost control, that value/policy must be decided before voice activation rather than invented by engineering.
